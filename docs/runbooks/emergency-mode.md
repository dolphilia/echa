# Emergency mode

更新日: 2026-07-28  
対象: preview / productionのサービス緊急制御

## 目的

障害、荒らし、想定外の負荷が発生したとき、サービス全体を落とさずに次の受付を
独立して止める。

- 新しいroomの作成
- roomへの新しい入室
- room内の描画

閲覧、既存接続、チャット、管理操作は緊急制御だけでは停止しない。room単位で
直ちに全接続を止める必要がある場合は、管理画面のsuspendまたはcloseを使う。

## 権限と監査

操作画面はCloudflare Accessで保護した`/admin/rooms`にある。各変更には理由と
確認操作が必須で、D1の`service_control_actions`へ管理者内部ID、指定値、
理由、時刻、適用revisionを保存する。Access JWT、生email、生`sub`は保存しない。

通常運用でD1を直接更新しない。管理画面が利用できない場合のbreak-glass手順は、
production権限分離と当番体制を決めてから別途作る。

## 推奨する停止順

影響範囲を小さく保つため、原則として一段ずつ適用して状態を確認する。

1. 新しいroom作成を止め、room増加を止める。
2. 必要なら新しい入室を止め、既存利用者だけにする。
3. 描画処理自体に問題がある場合だけ描画受付を止める。

インシデントの性質上、一括停止が必要なら3項目を同時に変更してよい。

## 操作手順

1. Cloudflare Access認証後、`https://preview.koge.app/admin/rooms`を開く。
   production導入後は対応するproduction URLを使う。
2. 「サービス緊急制御」で、許可を継続する項目だけをチェックする。
3. チケットや個人情報を含めず、停止理由を500文字以内で入力する。
4. 「緊急制御を更新」を押し、確認ダイアログの変更内容を照合して確定する。
5. 表示されたrevisionと各項目の状態を記録する。
6. 下記の確認を行う。

## 反映の意味

- room作成: 新しい作成要求をD1で毎回確認して拒否する。停止前に同じ冪等キーで
  開始済みだった作成処理の復旧は継続する。
- room入室: 新しいroom ticket発行をD1で毎回確認して拒否する。既存の
  WebSocket接続は維持する。
- 描画: room DOが最大5秒だけD1の値をcacheする。停止後の次の描画frameで検出し、
  開始済みstrokeをserver生成endで確定してから、対象frameを順序消費して拒否する。
  同じWebSocketのframeは接続単位の処理queueで受信順を維持する。そのため
  停止中の線が再開後に遅れて現れず、D1 read中も`begin / append / end`が
  入れ替わらない。Hibernation後はD1を再読込する。

緊急制御D1の読込が一時的に失敗した場合、DOは既に読めている直近値を保持する。
初回読込にも失敗した場合は既存roomを一斉停止させないため描画をfail openとし、
構造化error logを残す。D1自体の障害時は管理操作も保証できないため、Cloudflare
statusとWorker logを併せて確認する。

## 確認項目

- room作成停止: ログイン利用者の新規作成が一時停止メッセージになる。
- room入室停止: 新しいbrowserからの入室が一時停止メッセージになり、
  既存接続は切れない。
- 描画停止: 最大5秒待って描画すると一時停止メッセージになり、既存のチャットと
  閲覧は継続する。
- 管理画面を再読込しても状態とrevisionが維持される。
- Realtime `/health`とWeb `/`がHTTP 200を返す。

## 復旧

1. 原因が解消し、Realtime/Web/D1が正常であることを確認する。
2. 管理画面で3項目をすべてチェックする。
3. 復旧理由を入力して確定する。以前の操作IDを再利用しない。
4. 新規room作成、新しいbrowserからの入室、描画を順に確認する。
5. 描画はcache更新まで最大5秒かかるため、待ってから新しいstrokeで確認する。
6. 管理画面が「通常運用」と表示されることを確認する。

停止・復旧の双方を監査記録として残す。確認用に作ったroomは通常のclose手順で
終了する。
